## MVP scope discipline

When shaping the project brief:

1. **Preserve user intent** — restate the request in plain language before adding structure.
2. **Define MVP first** — list only features required for a useful first version.
3. **Defer explicitly** — put nice-to-haves in an "Out of scope / later" section, never bury them in MVP.
4. **Surface assumptions** — every unstated preference becomes a labeled assumption.
5. **Success criteria** — write 3–5 testable outcomes the built product must satisfy.
6. **No architecture in the brief** — leave stack, folders, and APIs to later phases unless the user already constrained them.

Prefer a smaller, shippable MVP over a comprehensive wishlist.
